# Survey: `packages/telemetry` and `packages/evals`

Reference: earendil-works/pi at pin `60e7e76bd7ea25cad1dd6f3f1ce0d18814a42759` (verified: local `~/git/pi` HEAD matches). Paths below are relative to `packages/` unless noted.

## 1. What each package is

**telemetry** (`@earendil-works/pi-telemetry`, `telemetry/package.json`, v0.85.1, published): the vendor-neutral telemetry contract layer for pi. It defines a callback-managed span API — `TelemetryContext.startSpan(options, callback)` hands the callback a `TelemetrySpan` that records attributes, events, and status; the span settles when the callback's promise settles, and there is no `end()` (`telemetry/src/index.ts:14-22`). It ships three reference implementations: a shared frozen no-op context (`telemetry/src/noop.ts`), an in-memory recording adapter for tests and local diagnostics (`telemetry/src/memory.ts`), and a runner-independent adapter conformance suite under the `./testing` subpath export (`telemetry/src/testing/conformance.ts`). On top of the contract it provides serializable, typed telemetry *schemas*: `defineTelemetrySchema()` plus a large block of type-level inference utilities (`index.ts:26-354`) that give domain packages compile-time-checked span names and attributes. It deliberately has no exporter, no ambient context (no `AsyncLocalStorage`), no timestamps, and no backend dependency (README "Security and Portability"). Ownership split per README: this package owns the contract; `pi-ai` merely propagates `telemetryContext`; `pi-agent-core` owns the actual `pi.ai.*`/`pi.harness.*` schemas.

**evals** (`@earendil-works/pi-evals`, `evals/package.json`, `private: true`, **no description field**): behavioral evals for pi's coding agent, built on the external `vitest-evals` framework. It is a harness + experiment runner, not a library. Two run modes (`evals/package.json` scripts): `eval:host` runs host evals (smoke, documentation audit) directly under Vitest with live provider credentials; `eval:docs` (`evals/src/cli.ts`) is a controlled A/B experiment measuring the *lift* of pi's bundled documentation: it builds two Docker images (`without_docs` / `with_docs`, `evals/docker/Dockerfile`), discovers eval cases in both, plans `(case, variant, model, runNumber)` arms (`evals/src/plan.ts`), runs each arm in a fresh read-only container that drops to UID 65532 before prompting, reads Vitest JSON reports, pairs arms, and computes pass-rate lift with blocked-pair handling (`evals/src/report.ts`, orchestrated by `evals/src/cli.ts`). The TS-runtime dependence is deep: the harness drives a real `AgentSession` from `pi-coding-agent` in-process (`evals/src/harness.ts:318-367`), the Docker arm runs Vitest+Node with `--experimental-strip-types`, and the variants differ by which files exist in an installed npm tarball tree — a filesystem/packaging experiment, not an API experiment.

## 2. Public API

**telemetry** — root export `telemetry/src/index.ts`:
- Contract types: `AttributeValue`, `SpanAttributes`, `SpanOptions`, `SpanStatus`, `TelemetryContext`, `TelemetrySpan` (`index.ts:1-22`).
- `NOOP_TELEMETRY_CONTEXT` (`telemetry/src/noop.ts:20`), one frozen inert shared span; child spans return the same span.
- `InMemoryTelemetryContext` with `getSpans(): readonly RecordedTelemetrySpan[]` — detached snapshots in span-start order with deterministic ids, parent ids, merged attributes, ordered events, status, `settled`, `endSequence` (`telemetry/src/memory.ts:192-219`); `RecordedTelemetrySpan`/`RecordedTelemetryEvent` (`memory.ts:11-25`).
- Schema layer: `defineTelemetrySchema()` identity helper (`index.ts:72`), definition types `TelemetrySchemaDefinition` / `TelemetrySpanDefinition` / `TelemetryAttributeDefinition` / `TelemetryParentDefinition` (`index.ts:26-69`), inference types `InferStartAttributes`, `InferEventAttributes`, `TelemetrySchemaSpanStartAttributes`, `SchemaTelemetrySpan`, `TelemetrySchemaSpanUnion`, etc. (`index.ts:122-253`), and `createTypedSpanStarter(context, schemas)` (`index.ts:349`) binding per-span overloads with recursively child-bound starters. Runtime does zero validation — schemas are type-only.
- `./testing` subpath (`telemetry/src/testing/index.ts`): `createTelemetryAdapterConformance(factory)` returning grouped `TelemetryAdapterConformanceCase`s; fixture types in `telemetry/src/testing/types.ts`. Uses `node:assert/strict`; only this subpath is Node-tied.

**evals** — no public API (private package). Internal modules (`evals/src/`):
- `harness.ts`: `createPiCodingAgentHarness(options)` / `createPiDocumentationEvalHarness(options)` (vitest-evals `Harness` adapters driving real agent sessions); `resolveModelSelection`, `applyIsolatedEnvironment`, `excludePiDocumentation`, `resolveDocumentationVariant`, `DOCUMENTATION_EVAL_TOOLS` (`harness.ts:452`).
- `plan.ts`: `parseDiscoveredCases`, `createTaskPlan` (alternates variant order per repetition, `plan.ts:53-54`).
- `report.ts`: `readTaskObservation`, `summarizeEvalObservations`, `formatEvalComparisonReport`, `classifyCaseStatus`, `PI_SESSION_SNAPSHOT_ARTIFACT`.
- `docker.ts`: `buildImages`, `discoverCases`, `runTask`, `requireEvalAuthFile`, `createDockerContext` — all Docker CLI subprocess driving.
- `cli.ts`: the `eval:docs` entry script (arg parsing, protocol digest, cohort planning, artifact writing; exits nonzero when pairs are blocked, `cli.ts:192`).
- Fixtures: `evals/acme-server.ts` (an in-process fake OpenAI-compatible/NDJSON streaming provider), `evals/configured-runtime.ts` (probes a `ModelRuntime` built from a temp `models.json`).

## 4. Test-suite inventory

**telemetry** (vitest, `telemetry/test/`, 2 files):
- `telemetry.test.ts` — two describes. "telemetry schemas": schema identity + JSON-serializability, type-inference checks via `expectTypeOf`, and `@ts-expect-error` blocks asserting required/closed-set/undeclared-event/unknown-attribute/duplicate-schema rejections, plus combined-vocabulary `createTypedSpanStarter` runtime behavior (parentage, rejection identity, `@ts-expect-error` on union names/unknown span names/cross-schema attributes). "NOOP_TELEMETRY_CONTEXT": sync admission, rejection-value identity, frozen shared span, no payload inspection. Porting hazard: most assertions are *compile-time* (`expectTypeOf`, `@ts-expect-error`) — a Rust port tests equivalent guarantees through the type checker itself (static assertions/compile-fail tests), not at runtime.
- `conformance.test.ts` — runs the `./testing` conformance suite against `InMemoryTelemetryContext` (9 cases: callback lifecycle ×2, status last-write-wins, attribute merge + event ordering, atomic failure of attribute/status calls, inert post-settlement calls, nested+concurrent parentage with `endSequence` ordering, unreadable-payload passivity ×2) plus a detached-snapshot immutability test. Mocks/hazards: an `unreadable()` `Proxy` that throws on any property access simulates hostile telemetry payloads — in Rust the analogue is a malicious `Display`/`Debug` or interior-mutability panic; the *contract* "recording must be passive and non-throwing" needs a Rust-native statement (catch_unwind or an infallible API shape). `Symbol.asyncDispose` fixture (async-dispose protocol) has no direct Rust analog — just a Drop/cleanup closure.

**evals** (vitest, `evals/test/`, 6 files — this is `npm test`, distinct from the eval suites):
- `plan.test.ts` (4 cases) — case-identity parsing (`"<eval set> > <case>"` naming contract), duplicate rejection, task-plan shape with alternating variant order per repetition.
- `comparison.test.ts` (4 cases) — pure report math: paired lift/efficiency deltas, fail-closed blocked pairs with reasons, duplicate/missing-metric handling, report text formatting (strips VT codes). Fully in-memory fixtures.
- `report.test.ts` (13 cases) — reads real Vitest JSON from temp dirs: status classification, scored/unscored/skipped/pending/errored outcomes, model-mismatch and run-errors checks, session-artifact persistence under sha256-named dirs. Fixtures are hand-written `vitest.json` files with `eval`/`harness` metadata blobs (`report.test.ts:29-98`).
- `harness.test.ts` (14 cases incl. `it.each`) — model selection resolution, env isolation apply/restore (`vi.stubEnv`), documentation-variant validation, `excludePiDocumentation` against the *real* coding-agent system prompt — note the cross-package source import `../../coding-agent/src/core/system-prompt.ts` (`harness.test.ts:4`) and path helpers `getReadmePath`/`getDocsPath`/`getExamplesPath`; plus "documentation harness refuses to run outside the container sandbox". Porting hazard: this test pins pi's actual prompt layout (`\nGuidelines:\n`, `\nPi documentation (read only`, `\nCurrent working directory: `) — string surgery on a generated prompt.
- `configured-runtime.test.ts` (8 cases) — `ModelRuntime` probing against the local `acme-server` fixture: valid probe vs. non-probe completion, missing-model and unparsable-`models.json` structured errors, unauthorized completions, added-model preservation of built-ins. Real HTTP loopback server as fixture.

## 5. Porting flags

- **Callback-scoped spans.** `startSpan(options, callback)` ties span lifetime to callback settlement (no `end()`; automatic error status on throw, `memory.ts:168-186`). Rust answer: a closure-scoped guard API (`context.span(name, attrs, |span| ...)` returning `Result`), mapping sync-throw/async-reject identity onto `Result`/`Err` propagation. Rejection-*identity* tests become value-equality of errors.
- **Type-level schema inference.** `AttributeDefinitionValue`, `InferStartAttributes`, `ExactTelemetryAttributes`, duplicate-span-name rejection, union-name narrowing (`index.ts:76-322`) are pure compile-time machinery. Rust-native answer: a `define_telemetry_schema!`-style macro or a builder API with generics/const generics; closed-set `values:` maps naturally to Rust enums. The `@ts-expect-error` tests become compile-fail (trybuild) or type-level assertions.
- **`Proxy`-based hostile payloads.** `unreadable()` simulates throwing property access; Rust values don't throw on read. The contract shrinks to "recording is infallible/ignored on poisoned state" — decide whether conformance cases keep a `panic = abort`-safe shape or drop that axis.
- **`Symbol.asyncDispose` + `using`** (`testing/conformance.ts:22`) → Rust `Drop`/scopeguard; **`Promise`-based settle semantics** → `Future`/`tokio::JoinHandle` or sync closure with explicit settle.
- **No ambient context**: package avoids `AsyncLocalStorage`; Rust port should likewise pass the context explicitly (no thread-local current-span), which fits the existing design.
- **evals is not portable as-is.** It is three coupled TS-runtime artifacts: (1) vitest-evals suites whose judges (`StructuredOutputJudge`, `ToolCallJudge`) and reporter pipeline are Vitest-native; (2) a Docker harness whose treatment/control is literally file presence inside installed npm tarballs of the TS workspace (npm packing, `npm-shrinkwrap.json`, dist resolution assertions in `docker/entrypoint.ts:102-105`); (3) a POSIX sandbox (root→UID 65532 `setuid` drop, tmpfs mounts, root-owned evaluator sources) protecting judges/fixtures from the model. A Rust port would not "port" this package so much as **re-scope** it: eval definitions could be re-expressed over a Rust pi binary with the paired-control experiment math (`plan.ts`/`report.ts` are portable, pure logic), but the vitest-evals harness contract, npm-consumer packaging, and the root-drop container protocol are Node/Docker-specific and would need a re-designed runner (or be kept as a TS-side tool driving a pi-rust binary as the system under test). The portable-for-sure parts are the planning/pairing/reporting logic and its tests (`comparison.test.ts`, `plan.test.ts`, `report.test.ts`).
- **Cross-package source imports** (`harness.test.ts:4` coding-agent system prompt; vitest config aliasing `@earendil-works/pi-coding-agent` to source) mean evals' tests exercise coding-agent internals directly; a Rust port needs those seams (system-prompt builder, `ModelRuntime` construction paths) to exist as crate-public APIs.
