# Rust extensions run out-of-process over a protocol session

The destination requires a Rust-native extension mechanism, and executing TS/JS extension files stays permanently out of scope, so upstream's in-process jiti loading has no Rust equivalent to port — the mechanism is designed, not ported. Decision, at upstream pin `60e7e76`: a third-party extension is a Rust binary the host spawns at startup, holding a versioned CBOR session over stdio on pi-protocol's substrate (the handshake refuses mismatched protocol versions exactly as the server does); first-party extensions compile into the binary and register directly, mirroring upstream's built-in llama.cpp extension. The extension API surface keeps everything upstream's `ExtensionAPI` exposes — all categories in scope, the 36 event channels mirrored 1:1 with sequential dispatch and per-event merge semantics, tools registered with JSON-Schema parameters (the wire contract unchanged) behind a schemars-backed typed helper. Distribution is dual-channel: `pi install crate:<name>@<version>` compiles the published source locally against the extension's committed lockfile, and `pi install github:...|tarball|path` fetches prebuilt executables; installs land disabled + untrusted and carry a hash receipt re-verified at every spawn, failing closed on any byte or protocol-version change. Trust itself ports 1:1 — per-directory `trust.json`, nearest-ancestor resolution, the prompt pipeline, and `project_trust` handlers. The extension mechanism and chord stay separate systems (upstream parity), so the `FacetModuleHost` loader seam's "facet bundle artifact" ownership transfers to the experimental remote-stack slice.

## Considered options

- **Compiled crate dependency** — extensions linked into the pi binary. Full API fidelity, but installing an extension requires rebuilding pi, which the effort ruled out.
- **Dynamic library + ABI-stable SDK** — the only in-process path without a rebuild. Research rejected it: `repr(Rust)` layout is unguaranteed across separately compiled dylibs, so the SDK becomes a parallel wrapper-type dialect (`RString`/`RVec`/vtables) regardless — the serialization ergonomics of the protocol boundary without its isolation; the machinery crates are unmaintained (abi_stable, three years) or carry open soundness reports (stabby); Bevy removed its dylib plugins "for being unsound"; the workspace `unsafe_code = "forbid"` would flip to `deny`, four of the 21 gates take structural damage (duplication headroom, duplicate-version denial, unproven dlopen coverage fixtures, mutation-testing blindness on `unsafe fn`), and macOS library validation refuses third-party dylibs in a hardened, notarized host. The process boundary is also the choice every comparable Rust agent made (Codex, CodeWhale).
- **WASM components** — sandboxed and ABI-free, but the same API re-expression burden over a WIT interface plus a large runtime dependency; the field uses it as a sandbox option, not the primary mechanism.

## Consequences

- UI crosses the wire as messages — pi-tui's line-based component shape (`render(width) → lines`, `handle_input`) bounds the protocol, and upstream's experimental chord stack already ships TUI facets over a wire; runner semantics become protocol round-trips, and UI-heavy overlays are the chattiest case.
- Crash isolation arrives: a failing extension dies alone and surfaces as a diagnostic, and the OS can confine the subprocess (Seatbelt/bwrap). Enforcement is deliberately deferred — sandboxing by default would break API parity for extensions that legitimately run shell and reach providers — but the boundary makes it possible, which no in-process model offers.
- The SDK surface is the extension module of `pi-coding-agent` (per ADR 0003, no new crate); extension crates depend on it the way upstream TS extensions peer-depend on the published packages. Publishing the SDK and pi-* crates to crates.io turns them into semver-stable public API — scope added to the package-manager slice, which also re-expresses the packages half over the new source grammar (the npm source kind drops; installer-safety rules for size caps, staging, path checks, atomic renames, and provenance markers carry over from the surveyed field practice).
- The npm channel's role (registry, discovery, `npm publish`) is taken by crates.io plus prebuilt release artifacts; the import tool maps TS npm package entries onto the new `packages` shape as skipped items, consistent with its existing decision.
